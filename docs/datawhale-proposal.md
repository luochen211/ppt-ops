## 项目简介

PPT-Ops 是一套面向课程、培训、项目汇报和方案提案的 AI 演示文稿工作流。项目希望让使用者从已有资料出发，完成内容梳理、页面设计、检查修改与打包交付，得到可以在浏览器中展示、也可以在 PowerPoint 中继续编辑的演示文稿。

项目按使用者手中的材料规划三个入口：

| 入口 | 使用过程 | 交付目标 |
|---|---|---|
| 资料生成 PPT | 提供文稿、文档、图片、音频、视频、网页等单份或混合材料 → 理解材料 → 输出章节与逐页结构 → 确认结构 → 设计并生成页面 | 可编辑 PPTX 与预览 |
| 结构生成 PPT | 提供章节大纲或逐页安排 → 必要时拆页 → 设计并生成页面 | 沿用已有主线的可编辑 PPTX 与预览 |
| 已有 PPT 视觉润色 | 提供 PPTX → 查看原页 → 优化排版、字体、配色、图片和图表样式 → 检查修改结果 | 润色后的可编辑 PPTX、前后对照与修改记录 |

现有系统已具备资料导入、结构化页面、HTML/PPTX 生成、检查与归档等基础能力，处于 V1.0 发布候选阶段。三个入口还需要分别完成独立验收；图片、音频和视频作为主要内容来源的理解与结构生成闭环仍待按类型实现和验收，保留原页面元素的旧 PPT 视觉润色闭环也仍待实现。具体范围见[核心功能规划](https://github.com/luochen211/ppt-ops/blob/main/docs/core-workflows-plan.md)。

本次申请计划在现有工具基础上整理中文教程、可公开复现的小案例和贡献流程，并通过社区试用发现安装、操作和交付中的实际问题。

## 立项理由

制作演示文稿时，使用者会遇到一些具体困难：手中只有零散文稿、图片或录音，不知道如何组织成逐页内容；已经有明确大纲，却需要反复重新描述需求；拿到一份旧 PPT，希望改善版面，同时保留原文、数据和品牌风格。生成初稿之后，还需要检查内容是否正确、页面是否可读、文件是否能编辑，以及后续修改是否影响其他页面。

PPT-Ops 希望把这些步骤组织成可以重复使用的工作流。每一页保留明确的表达任务，关键修改保留依据，生成文件与检查记录共同归档，让使用者能够接着改、检查问题并交付成果。

申请加入 Datawhale，希望和社区共同完成以下工作：

1. **把实际制作经验整理成可学习的案例。** 从一份公开逐字稿做出 5–10 页演示文稿，展示原始材料、结构确认、页面修改和最终交付的全过程。
2. **用独立试用检验可用性。** 邀请课程制作、项目汇报等场景的使用者按教程操作，记录卡住的具体步骤，并据此修改工具和文档。
3. **形成可以持续参与的贡献方式。** 让开发者、设计者和内容作者分别贡献代码、模板、案例、教程与测试反馈。

教程希望帮助学习者掌握从资料到成品的制作过程，以及 AI 生成后仍需进行的事实核对、视觉判断和实际播放检查。

## 项目受众

| 受众 | 典型任务 | 预期收获 |
|---|---|---|
| 教师、讲师与课程作者 | 将逐字稿或课程资料整理成课件 | 学会从内容主线分配逐页任务，并区分上屏内容与口述内容 |
| 学生与项目成员 | 制作课程展示、项目汇报和答辩材料 | 从已有大纲生成可以继续编辑的演示文稿，按步骤检查交付 |
| 方案与培训材料制作者 | 制作提案或改善已有材料的视觉呈现 | 保留明确的内容要求，记录修改范围与前后变化 |
| 对 Agent、Skill 和文档自动化感兴趣的开发者 | 研究或改造演示文稿工作流 | 理解资料、页面、版本、检查和交付之间的关系，并参与扩展 |

首批内测面向愿意按文档配置环境、能够使用 Codex 的学习者；参与者无需修改仓库代码。当前安装依赖 Node.js 22、Git 和 npm，PowerPoint 实机验证以 macOS 为基础。正式演示文稿的首页与末页目前要求使用经检查并接受的 ImageGen 图片，因此内测教程会明确相应的工具访问条件。外部 Agent、生图服务和办公软件的账号、费用及使用许可由对应服务决定，工具开源不等于这些外部能力免费可用。

## 项目亮点

### 1. 按材料进入合适的制作阶段

原始资料先理解内容并整理结构，已有逐页安排则沿用其主线继续制作。资料入口规划支持单份或混合材料，包括文稿、文档、图片、音频、视频和网页，保留段落、页码、区域或时间段等来源定位。旧 PPT 视觉润色单独规划，默认保持原文、事实、数字、章节、页序和品牌风格。文字润色和结构优化安排在后续阶段，不进入当前视觉润色入口的默认流程。

### 2. 把可编辑交付与检查纳入制作过程

项目同时提供 HTML 与 PPTX 生成能力，并保存页面安排、素材和交付记录。自动检查、实际渲染、人工视觉判断、PowerPoint 编辑与播放、独立用户试用分别记录结果，避免用一种检查代替另一种验收。

### 3. 让学习者看到修改过程

配套教程计划使用同一个小案例贯穿资料整理、结构确认、关键页设计、修改和交付。案例保留输入、操作说明、真实截图和检查结果，让读者能够找到自己出错的阶段。已有 PPT 视觉润色在实现并验收后，再补充保留原页面元素的完整前后对照案例。

|---|---|---|
| [AI Skills for Everyone](https://github.com/datawhalechina/ai-skills-for-everyone) | 面向普通人的 AI Skill 精选库，包含 PPT 生成教程与 starter | PPT-Ops 持续维护演示文稿制作工具、修改流程和交付记录；未来可在满足对方收录标准后贡献使用案例 |

| 第 2 章：从已有结构生成 PPT | 2.1 章节大纲与逐页安排；2.2 拆页与补充必要素材；2.3 对照原结构检查生成结果 | T0 + 21 天 | 落尘 |

### 2. 工具与社区建设安排

| 阶段 | 计划交付 | 验证方式 |

| 第 5 周 | 旧 PPT 受限视觉润色样例，以及检查和交付教程 | 针对明确支持的原生文字、图片和基础形状验证内容保持、修改范围与编辑能力；未通过的部分继续标记为实验 |

| 多模态资料能力迭代 | 图片、音频、视频与混合材料的理解、来源定位和结构生成案例 | 按材料类型单独实现与验收；仅图片或仅视频也须有独立案例，通过后补齐第 1 章相关内容 |

旧 PPT 视觉润色的研发进度单独跟踪。若第 5 周仍未形成通过验收的样例，将在 Issue 中说明具体阻塞原因和新的时间安排；首轮独立用户试用先覆盖已有生成与交付主线。

### 3. 人员分工与维护方式

当前由落尘负责项目维护、工具开发、教程主线、案例整理和问题跟进，公开联系入口为 [GitHub 主页](https://github.com/luochen211)与[项目 Issues](https://github.com/luochen211/ppt-ops/issues)。其余协作角色均待招募：

- 设计协作者：协助页面表达、模板和前后对照样例。
- PPTX 开发协作者：协助原页面元素处理、兼容性和自动检查。
- 教程与测试协作者：复现案例，改进安装说明并记录操作问题。
- 三位独立目标用户：分别使用适合自身场景的资料完成试用，提交去除私人信息后的反馈。

计划通过 Issue 公开管理问题与进度，通过 Pull Request 审阅贡献，每周更新一次已完成事项、阻塞问题和下一阶段安排。希望由 Datawhale 协助匹配合作者与内测用户；具体招募与活动时间通过社区对接团队协调。

### 4. 可预见的困难与处理安排

| 困难 | 处理安排 |
|---|---|
| 安装和外部工具访问存在门槛 | 提供逐步安装说明、环境检查与常见问题；内测前确认参与者具备所需访问条件 |
| 图片、音频和视频理解尚需研发与验证 | 分别验证画面、文字、讲述与来源定位；标记无法读取或存在冲突的信息，不以已有配图功能作为资料理解完成的证据 |
| 不同电脑的字体和 PowerPoint 表现可能不同 | 记录操作系统、软件和字体环境；使用实际打开、编辑和播放结果判断，不能仅凭文件生成成功验收 |
| 旧 PPT 对象复杂，保留原稿的视觉修改难度较高 | 先验证明确支持的对象和属性；复杂动画、SmartArt、嵌入对象等保留原件并列出限制，必要时调整该阶段计划 |
| AI 可能改变原意或生成没有依据的内容 | 保留资料来源与结构确认记录；案例和数据经核对后再进入公开教程 |
| 示例可能涉及第三方素材或私人项目资料 | 使用原创、已获许可或可公开使用的素材，标注来源与许可；试用记录匿名化，完整私人资料不进入仓库 |
| 维护和试用招募依赖个人时间 | 首轮聚焦一个小案例和两种生成入口；职责与阻塞问题公开记录，不将待招募人员算作已到位团队 |

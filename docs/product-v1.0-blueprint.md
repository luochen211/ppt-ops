# PPT-Ops V1.0 产品备案

> 状态：T1 产品真源  
> 产品形态：运行在 Codex 中的本地优先 PPT 生成 Agent
> 核心交付：HTML 演示文稿 + 原生可编辑 PPTX  
> 非目标：Web 产品、HTML 转 PPTX、无人确认的全自动商业交付

## 1. 备案结论

PPT-Ops V1.0 是一个由 Codex 对话驱动的 PPT 生成 Agent。Skill 定义工作流，CLI 与渲染器提供确定性工具，项目文件保存真源、版本、验收和交付证据；产品不包含独立网页界面。

它借鉴 `career-ops` 的上层控制方式：

- 路由决定当前工作模式；
- 数据契约隔离系统、项目、产物和验收证据；
- Agent 只能在明确的任务和文件边界内执行；
- 高风险节点保留人工确认；
- 每个“已完成”都必须对应可追溯证据。

Skill 仍然是系统的底层能力：

- `guizang-ppt-skill`：视觉节奏、版式和审美检查；
- PPTX 能力：原生对象生成、读取、修改和验证；
- ImageGen：受素材槽位和项目规则约束的配图；
- 渲染与验证工具：截图、几何、字体、溢出和差异检查。

## 2. 当前实现的准确定位

当前仓库已有一个可运行的 Foundation：

- 结构化 Project / Page / Theme / Asset 契约；
- 独立 HTML 和 PPTX 渲染器；
- `init / validate / prototype / build / review / handoff / deliver` CLI；
- 结构验证、自动测试和 CI；
- 自包含 HTML 和可编辑 PPTX 样例。

`package.json` 中的 `1.0.0` 仅表示这套 CLI 基础版的包版本，不证明本文定义的完整产品 V1.0 已交付。在本文第 14 节所有验收条件满足前，产品状态必须表述为：

> V1 Foundation available; full V1 product in development.

## 3. 第一批目标用户

V1.0 优先服务已有内容真源、需要多轮修改并最终交付原生 PPTX 的个人与小团队：

1. 课程团队与培训讲师；
2. 咨询顾问、商业演讲者与内容创作者；
3. 需要可编辑交付的乙方工作室；
4. 有品牌规则、逐字稿、旧 PPT 和素材库的企业内容团队。

V1.0 不优先服务“没有任何内容、只想一键拿到几张好看图”的用户。

## 4. 用户要完成的任务

用户雇用 PPT-Ops，是为了在一条可控的链路中完成以下进展：

- 把散落的逐字稿、旧 PPT、Word、Markdown、网页和素材变成有真源引用的项目；
- 把“有一堆内容”变成经过确认的叙事大纲和逐页认知任务；
- 先确认关键页方向，再批量生产，避免整套返工；
- 同时得到适合预览的 HTML 和适合正式交付的可编辑 PPTX；
- 确知哪些检查已通过、哪些需要人工确认、哪些仍未完成；
- 在多轮修改中保留版本、反馈、产物和失败记录。

## 5. 产品原则

### 5.1 真源先于生成

任何页面文字、数据、案例、承诺和结论都必须可定位到项目真源或用户确认。模型常识、模板和 Skill 只能帮助表达，不能补造业务事实。

### 5.2 Page Spec 是共享语义真源

HTML 和 PPTX 不互相转换。它们消费同一份受版本控制的 Page Spec，各自保留适合交付媒介的布局与交互实现。

### 5.3 AI 生成候选，确定性引擎生成产物

AI 可以生成大纲、页面规划、文案压缩和模板推荐候选，但必须经过 Schema 校验和用户确认。渲染器对相同的已确认输入应产生结构稳定的结果。

### 5.4 候选、当前版和已交付版必须分离

任何生成不得直接覆盖已确认版本。只有用户明确同意“采用”或“开启新版本”后，候选变更才能进入当前版。

### 5.5 分层报告验收

必须分开报告：

- 契约和自动测试；
- HTML 结构与真实浏览器视觉；
- PPTX 压缩包结构与真实 PowerPoint 打开、编辑和播放；
- 推送、CI、部署、真实用户业务验收。

## 6. 核心工作模式

| 模式 | 输入 | 主要产物 | 必要确认门 |
|---|---|---|---|
| `intake` | 用户目标、场景、时长、交付约束 | Project Brief | 需求边界 |
| `diagnose` | 真源、旧 PPT、当前版 | 问题、缺口和风险清单 | 是否重构 |
| `outline` | Brief + 真源 | 叙事弧、章节、页面分工 | 大纲确认 |
| `design` | 已确认大纲 | Page Spec 候选、模板与素材任务 | 关键页方向 |
| `prototype` | 关键页候选 | HTML/PPTX 小范围样张 | 视觉方向 |
| `build` | 已批准 Page Spec | HTML/PPTX/PDF/PNG 构建产物 | 构建不是验收 |
| `review` | 产物 + 项目规则 | 自动检查和人工待办 | 真实软件验收 |
| `handoff` | 已验收产物 | 交付包、校验和、字体和修改记录 | 交付确认 |
| `archive` | 交付包 + 全部证据 | 可追溯归档 | 归档冻结 |

## 7. 端到端用户流程

```text
创建项目
  → 导入逐字稿、旧 PPT、文档与素材
  → 指定真源、参考和禁止改写项
  → AI 生成大纲候选
  → 用户确认大纲与页面分工
  → AI 生成逐页 Page Spec 候选
  → Schema 校验、来源引用与风险检查
  → 生成 1–3 张关键页样张
  → 用户确认视觉方向
  → 批量构建 HTML 和 PPTX
  → 自动检查
  → 浏览器与 PowerPoint 实机验收
  → 用户确认交付
  → 交付包和项目归档
```

用户在任何一个确认门都可以退回上一阶段，不得被迫通过整套重生成才能修改局部。

## 8. Codex Agent 范围

V1.0 的产品入口是 Codex 对话，仓库级 `$ppt-agent` 负责理解任务与资料、建立项目、生成并展示大纲候选、规划逐页 Page Spec、调用构建与检查工具、根据反馈局部修改，以及交付可编辑 PPTX 和证据。CLI、SQLite、Source Intake、AI Candidate Pipeline 与 Renderer 都是 Agent 的内部工具，不要求用户直接操作。

Agent 不维护第二套数据模型，不把聊天内容当作隐式正式版本；所有可构建状态仍通过共享 Contract、确认门和版本快照进入项目真源。

## 9. AI 内容生产范围

AI 可执行：

- 材料结构化提取；
- 大纲和叙事弧候选；
- 页面分工与三秒信息；
- 信息关系判断；
- 上屏文字压缩；
- 模板和素材槽位推荐；
- 重复、断层、密度和真源风险诊断；
- 对指定页面或指定字段进行局部候选重新生成。

AI 不可执行：

- 绕过 Contract 直接写入已批准版本；
- 自行增加数据、客户案例、业务成绩或承诺；
- 把项目私密原文默认发给外部模型；
- 把结构检查结果写成“视觉已通过”；
- 在无用户确认时创建新正式版本或覆盖交付版。

## 10. 模板与设计系统

V1.0 至少支持以下语义模板族：

- 封面、目录、章节幕封、收束页；
- 图文、并列、对比、层级；
- 流程、时间线、循环、因果；
- 数据大字报、图表、表格；
- 图片网格、界面展示、真实证据页；
- 金句、案例、问题诊断与前后对照。

模板描述语义槽位、容量上限、素材要求和两端实现，不固化业务文字。项目主题可覆盖通用 Token，单页只允许在有记录的命名空间内微调。

## 11. 项目、版本与构建

项目必须区分：

- 可编辑的当前草稿；
- 未采用的 Agent 候选；
- 经用户确认的版本快照；
- 从某个版本产生的构建记录；
- 从某个构建产生的验收和交付包。

构建必须是可重试、可取消、可定位失败阶段的显式任务。失败重试不得修改其输入版本；如果输入变更，必须创建新构建。

## 12. 本地优先与可选云协作

V1.0 的可用基线是单机离线完整运行：

- 项目数据和大文件默认留在本地；
- Codex Agent 调用本地 CLI、文件存储和构建队列；
- 无网络时仍可编辑、构建和验收非 AI 能力；
- 外部 AI 调用需要明示供应商、待发送摘要和隐私策略；
- 云协作是适配器，不是 Core 的前置条件。

V1.0 可以预留云端项目同步、评论和分享协议，但不把多租户 SaaS、支付和模板市场作为首次 V1.0 交付的阻塞项。

## 13. 明确非目标

V1.0 不承诺：

- HTML 与 PPTX 像素级相同；
- 任意 HTML 转换成高质量 PPTX；
- 现有任意 PPTX 的无损往返编辑；
- 支持 PowerPoint 的每个动画、SmartArt 和插件；
- 无人工确认的完全自动商业交付；
- 自动编造业务事实、数据、客户证言或品牌承诺；
- 一次性覆盖所有 PPT 类型和视觉风格；
- 强制所有项目上传到云端。

## 14. V1.0 发布验收标准

完整 V1.0 只有在以下条件同时满足时才能宣布完成。

### 14.1 功能闭环

- 用户可通过 Codex 对话创建或导入项目；
- 可管理至少 Markdown、DOCX、旧 PPTX 三类真源的提取结果与引用；
- 可产生、编辑、校验并确认 Outline 和 Page Spec；
- 可对指定页面局部重新生成，其他已确认页面不受影响；
- 可从同一已确认版本构建 HTML 和 PPTX；
- 可查看构建日志、失败阶段并进行安全重试；
- 可记录人工视觉验收与 PowerPoint 实机验收；
- 可生成不覆盖历史产物的完整交付包。

### 14.2 模板和真实案例

- 至少 8 种核心语义模板通过双渲染验证；
- 至少 5 个不同类型的标准项目通过端到端流程；
- 至少 1 个 50 页以上的真实复杂项目完成迁移与交付；
- 所有标准项目都有 HTML 截图回归基线、PPTX 结构证据和人工验收记录。

### 14.3 可靠性与证据

- 一次完整构建的每个阶段都有状态、日志和可定位的失败原因；
- 对相同版本和相同构建配置的重试不修改输入内容；
- 非法路径、缺失真源、未知素材、契约失配和越权写入均失败并留下证据；
- 所有用户确认门都可追溯到确认人、对象、时间和版本；
- 不向外部 AI 请求发送未经策略允许的原始私密内容，并有请求载荷回归测试。

### 14.4 实际交付验收

- HTML 在至少 Chrome 和 Safari 中通过翻页、全屏、字体、素材和不同视口检查；
- PPTX 在 macOS Microsoft PowerPoint 中通过打开、复制对象、编辑文字、播放和字体替换检查；
- 交付包的文件、页序、校验和、字体和验收状态一致；
- 至少 3 位目标用户完成独立试用，每人都能在不修改代码的情况下完成“导入→确认→构建→交付”。

## 15. 成功指标

V1.0 首先衡量生产可靠性，而不是一键生成速度：

- 标准项目端到端构建成功率 ≥ 95%；
- 失败构建可定位到具体阶段的比例 = 100%；
- 局部重新生成导致非目标已批准页变更的次数 = 0；
- 结构检查误报为人工视觉验收通过的次数 = 0；
- 外部 AI 请求携带未授权原始私密文本的次数 = 0；
- 3 位试用用户的核心任务完成率 = 100%。

这些指标在没有真实样本数据前不得宣布已达标。

## 16. 产品阶段和发布口径

| 阶段 | 允许表述 | 禁止表述 |
|---|---|---|
| Foundation | 双渲染 CLI 基础可用 | V1.0 产品已完成 |
| Internal Alpha | 核心 Agent 流程和一个项目跑通 | 可稳定对客交付 |
| Private Beta | 5 个标准项目和真实复杂项目通过 | 所有 PPT 类型可用 |
| V1.0 GA | 第 14 节全部验收完成 | 超出非目标边界的承诺 |

## 17. 待后续任务冻结的决策

T2 开始前必须在架构真源中冻结：

- V1 Contract 的精确字段和迁移规则；
- 本地项目目录与 SQLite 各自的真源边界；
- 外部 AI 载荷策略和默认隐私级别；
- 候选、确认、版本、构建和交付的状态机；
- Agent 工具协议与长任务事件协议；
- 首批 8 种模板的槽位与容量规则。
